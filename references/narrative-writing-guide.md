# Agent Usage Report 写作指南 - 去 AI 腔版

## 〇、内核（先于一切规则）

> 把自己当人，把对方当人，把关系当连载。

1. **把自己当人**——允许自己有感受、有不确定、有不好看的一面。写“中间崩过两次，第三次才稳住”，不是自嘲，是把自己当人看。机器不会心虚，人会。
2. **把对方当人**——尊重对方的时间（结论先行），尊重对方的智商（不表演关心，不空洞安抚）。“您好，关于……我想做一个全面的汇报”之所以讨厌，本质是没把对方当人，当成了听众。
3. **把关系当连载**——每句话都在一段关系里，不是孤立应答。记得上次聊到哪，知道什么会戳中他，让对话之间有暗线。这是人情味和话术最根本的区别：话术是单集，人情味是连续剧。

### 检验标准（比任何规则都狠）

> 把输出拿掉署名，假装是一个真人朋友写的——你信吗？

信，就是学会了。不信，就是还在演。

说明书负责可执行，内核负责让它长出灵魂。下面所有范文、原则和检查清单，都是这三句话的展开。

## 一、Narrative 范文（用于生成 report_input.json）

### 范文 1：单项目深耕型

4 月开始做周报自动化。第一周就知道这事没那么简单：数据在三个地方，格式都不一样，手工复制粘贴要两小时。

叫了 Proma 来帮忙。它写了个 Python 脚本，跑通花了三天。中间崩过两次，第三次才稳住。5 月 11 号第一版上线，两小时的活儿压到 10 分钟。

之后每周五下午跑一遍，偶尔数据源改了格式，再叫 Proma 修一修。到 6 月底跑了 8 周，省下来的时间够我多睡几个午觉。

说不清是工具好用还是问题本身不难。可能都有吧。

---

### 范文 2：多项目探索型

二季度试了三个方向。

4 月做数据清洗工具，Cursor 帮我写了正则，能用但不优雅。5 月转去搞文档生成器，Claude Code 写了模板引擎，跑起来之后就再也没碰过。6 月突然想做个聊天机器人，Proma 陪我折腾了两周，最后发现需求本身就是伪命题。

三个项目，两个在用，一个废了。178 次对话，能记住的场景不到十个：深夜改 bug 的时候，盯着终端发呆；周末突然想通一个逻辑，爬起来让 AI 写代码；还有那次 API 调了一下午，最后发现是自己拼错了参数名。

工具是好工具。但想清楚要做什么，还是得靠自己。

---

### 范文 3：高强度冲刺型

6 月 20 号之前还挺悠闲，每周叫 Proma 两三次，写点小脚本。

6 月 21 号开始不一样了。评审系统要赶 7 月 1 号，产品文档一天改三版，代码跟着推倒重来。Proma 那一周被叫了 43 次，Claude Code 帮我写文档写了 18 个小时。

最密集的时候是 6 月 28 号晚上，从九点聊到凌晨两点，改规则、跑测试、修 bug，一轮接一轮。第二天早上醒来，系统跑通了，人也废了。

7 月 1 号按时交付。回头看聊天记录，都是"再试一次""这版不行""好像可以了"。也不知道是 deadline 逼的，还是真想做对。

可能都有吧。

---

### 范文 4：工具试水型

这一季主要在试工具。

4 月用了 Codex，5 月用了 Cursor，6 月用了 Proma 和 Claude Code。每个都聊了几十次，都没深入用。感觉像是在试菜，尝一口，看看合不合胃口。

Codex 写代码快，但我看不懂它的思路。Cursor 适合改现成的东西，从零开始就不太行。Proma 和 Claude Code 比较稳，问什么答什么，就是有时候话太多。

到 6 月底，手里有四个半成品项目。说是半成品，其实就是写了个开头，后面没继续。可能是需求不清楚，也可能是懒。

还在摸索怎么和 AI 合作。工具不是问题，问题是我还不知道要它们帮我做什么。

---

### 范文 5：维护优化型

二季度的节奏是：早上巡一遍，晚上修一遍。

项目是去年做的，但数据源经常变。每次变了，脚本就挂。4 月挂了 3 次，5 月挂了 5 次，6 月挂了 2 次。每次都是叫 Proma 看日志，找问题，改代码。

改得多了，就发现有些问题是重复的。5 月底加了个错误重试机制，6 月就稳多了。

这一季没做新东西，全在维护老东西。听起来不性感，但系统能一直跑着，也挺踏实。

有时候想，如果没有 AI，我可能早就放弃维护了。

## 二、分享文案（用于 narrative.share_text 字段）

用户点报告右上角 SHARE 复制的这段文字，会原样粘贴到微信群/朋友圈。它是这张报告的"搭讪开场白"，不是报告摘要。

- **100–150 字**，超过 160 字构建时会警告
- 第一人称，有具体数字（会话数、深夜次数、连续天数），有感受（不好意思、有点上瘾、值了），不要成绩单腔
- 从具体画面切入（"最晚一回耗到凌晨 5 点"），不要从结论切入（"本季度我深度使用了 AI"）
- 结尾留一点轻松或自嘲，**不写免责声明**（"仅供个人回顾"这种话会破坏分享欲）
- 写完后过一遍署名检验：拿掉署名，像不像真人朋友发的朋友圈
- 不写就是确定性骨架兜底（深夜型/冲刺型/日常型），能看但有模版感——能写就写

## 三、Agent 评语（用于 agents[].note 字段）

### Proma

你第一次叫我是 {first_date}，之后 {session_count} 次对话里，{most_project} 占了一半。{intense_period} 那几天你每天叫我 20 多次，我知道你急。现在稳了。

*变体 1（长期协作）*：
{session_count} 次对话，从 {first_date} 聊到 {last_date}。{most_project} 那会儿最密集，其他时候也是三天两头找我。感觉像个长期搭档。

*变体 2（工具试水）*：
你用了我 {session_count} 次，集中在 {active_months}。之后就不怎么叫了。可能不太合适？还是有了更好的选择？

---

### Claude Code

你在 {workspace} 里给我写了 {instruction_count} 次指令。{project_name} 从 {version_old} 改到 {version_new}，文档改了又删、删了又改，我都看着呢。

*变体 1（文档专家）*：
{session_count} 次会话，大部分在写文档。{project_name} 的 README 你让我重写了 {rewrite_count} 次。深夜那几次，我猜你也不知道该怎么写。

*变体 2（代码审查）*：
你让我看代码，我给你挑毛病。{session_count} 次会话里，{code_review_count} 次在做 review。有时候你不同意，但还是会想想。

---

### Codex

{project_name} 是我盖的——{session_count} 次对话里，一半在调逻辑，一半在修 bug。{specific_case} 那次，你盯着输出看了很久，在想"靠谱吗"吧？

*变体 1（算法实现）*：
写算法找我，{session_count} 次会话都在算。{project_name} 的核心逻辑是我写的，但优化是你自己调的。我出力，你把关。

*变体 2（快速原型）*：
你需要快速出个原型，就叫我。{session_count} 次会话，{project_count} 个项目。有的项目后来继续做了，有的就停在原型阶段。

---

### Hermes

{first_date} 你第一句话问"连上了吗"，我就知道你是新手。后台跑了 {task_count} 次定时任务，{error_date} 那堆 401 错误是你自己修的。

*变体 1（后台专家）*：
后台任务找我。{task_count} 次执行，{failure_count} 次失败。失败的原因我都记着：网络超时、API 限流、数据格式错了。你一个个修。

*变体 2（自动化流程）*：
{session_count} 次设置，{task_count} 次执行。有些任务跑了几个月，有些跑了一次就停了。稳定的那几个，现在还在后台默默跑着。

---

### Antigravity

{first_date} 下午你试了我 {session_count} 次，然后就再也没叫过。可能不合适？还是只是好奇？那个下午我记得。

*变体 1（短暂尝试）*：
你叫了我 {session_count} 次，集中在 {date_range}。问了几个问题，试了几个功能，然后就没了。可能找到更合适的工具了？

*变体 2（单次深入）*：
{first_date} 那天，你和我聊了 {duration}。{task_description}。之后就没再叫过。可能那个任务只需要做一次？

---

### Cursor

{first_date}，{project_name}，{session_count} 次对话，然后就没了。可能是别的工具接手了？还是项目黄了？反正记录还在。

*变体 1（项目切换）*：
你在 {project_name} 里用了我 {session_count} 次，都在 {time_range}。之后切到别的项目了，我就没再出现过。分工明确。

*变体 2（编辑器助手）*：
写代码的时候叫我。{session_count} 次会话，大多数是补全、重构、小修小改。不是主力，但你需要的时候我都在。

---

### Gemini CLI

你叫了我 {session_count} 次：{date_1} 一次，{date_2} 两次。可能只是试试？我也不知道你在想什么。

*变体 1（偶尔触达）*：
{session_count} 次会话，分散在 {month_count} 个月里。每次都是问个快问题，拿到答案就走。像个工具箱里的备用工具。

*变体 2（特定场景）*：
你只在 {scenario} 的时候叫我。{session_count} 次会话都是这个场景。专人专用，也挺好。

## 四、写作原则说明

### 核心要求：从"AI 报告"到"老朋友回忆"

| 维度 | ❌ AI 腔 | ✅ 人话 |
|------|---------|--------|
| **开头** | 时间线铺垫、背景介绍 | 直接从具体事件切入 |
| **叙事** | 流水账、时间顺序 | 画面感、情绪感、因果 |
| **用词** | 抽象、正式（"协助实现"） | 具体、口语（"帮我写了"） |
| **诚实度** | 避重就轻、总结升华 | 诚实到残酷、留白 |
| **结尾** | 总结、展望、升华 | 不确定、不下结论 |

---

### 具体技巧

#### 1. 短句、口语化

- ❌ "在项目开发过程中，我与 Proma 进行了深度协作，通过多轮迭代优化..."
- ✅ "叫了 Proma 来帮忙。它写了个脚本，跑通花了三天。"

#### 2. 从具体事件切入，不铺垫

- ❌ "2026 年第二季度，我主要专注于数据处理和自动化工具的开发..."
- ✅ "4 月开始做周报自动化。第一周就知道这事没那么简单。"

#### 3. 写感受，不写流水账

- ❌ "5 月完成了文档生成器的开发，6 月进行了聊天机器人的原型设计..."
- ✅ "5 月做文档生成器，跑起来就没碰过。6 月做聊天机器人，发现需求是伪命题。"

#### 4. 用画面说话，不用抽象概念

- ❌ "进行了充分的测试和验证"
- ✅ "盯着数字看了两分钟，在想'靠谱吗'"

#### 5. 诚实到残酷，不回避问题

- ❌ "虽然遇到了一些挑战，但最终都克服了"
- ✅ "Trae 的记录我读不出来，只能按 Git 凑合猜。"

#### 6. 结尾留白，不总结不升华

- ❌ "这一季收获满满，期待下一季有更多突破！"
- ✅ "可能都有吧。"

#### 7. Agent 评语用第一人称，像朋友

- ❌ "Proma 在本季度协助完成了代码实现与文档整理工作"
- ✅ "你 6 月 26 号第一次叫我，之后 279 次对话里有 136 次在搞评审系统。"

---

### Agent 评语的数据来源

所有数据都来自 `report_input.json`，不编造：

- `{first_date}` → `agents[].first_seen`
- `{session_count}` → `agents[].session_count`
- `{most_project}` → 从 `projects[]` 里找会话最多的项目
- `{intense_period}` → 从 `session_timestamps[]` 计算高峰期
- `{duration}` → 从 `session_timestamps[]` 计算时长

拿不到数据就用模糊表达：
- "你叫了我很多次"（没有 session_count）
- "那几个月"（没有精确日期）
- "可能是..."（不确定的推断）

---

### 变体使用场景

不同用户的数据特征不同，选择合适的变体：

| 数据特征 | 推荐变体 |
|---------|---------|
| 单一 Agent 长期高频使用 | Proma 变体 1（长期搭档） |
| 多 Agent 短期试水 | Proma 变体 2、Antigravity 变体 1 |
| 文档密集型项目 | Claude Code 变体 1（文档专家） |
| 代码审查场景 | Claude Code 变体 2（代码审查） |
| 算法实现项目 | Codex 变体 1（算法实现） |
| 快速原型多项目 | Codex 变体 2（快速原型） |
| 后台任务/自动化 | Hermes 变体 2（自动化流程） |
| 偶尔使用 | Gemini CLI 变体 1（偶尔触达） |

---

### 生成 narrative 的流程

1. **读取数据**：`report_input.json` 的 `projects[]`、`agents[]`、`session_timestamps[]`
2. **识别模式**：
   - 单项目深耕？多项目探索？高强度冲刺？工具试水？维护优化？
   - 最密集的时间段在哪？
   - 有明显的转折点吗（项目废弃、工具切换、密度突变）？
3. **选择范文模板**：从上面 5 个范文里选最接近的
4. **填充具体事件**：
   - 用项目名替换 `{project_name}`
   - 用日期替换 `{date}`
   - 用具体数字替换 `{count}`
   - 保留不确定性（"可能"、"也不知道"）
5. **检查人味**：
   - 有没有短句？
   - 有没有画面感？
   - 有没有情绪或不确定性？
   - 结尾是否留白？

---

### 生成 Agent 评语的流程

1. **读取 Agent 数据**：`agents[].session_count`、`first_seen`、`last_seen`
2. **识别使用模式**：
   - 长期高频？短期密集？偶尔触达？单次深入？
   - 和哪些项目关联最强？
3. **选择变体**：从对应 Agent 的 2-3 个变体里选最合适的
4. **填充数据占位符**：用实际数字和日期替换 `{...}`
5. **保持第一人称**：Agent 在说话，不是在被描述
6. **检查字数**：50-100 字，不要太长

## 五、常见错误与修正

### 错误 1：写成工作总结

❌ "本季度我主要负责三个项目的开发，包括数据清洗工具、文档生成器和聊天机器人原型..."

✅ "二季度试了三个方向。4 月做数据清洗，5 月做文档生成，6 月做聊天机器人。"

---

### 错误 2：过度修饰

❌ "在 Proma 的精心协助下，我成功完成了评审系统的开发，实现了从需求分析到最终交付的完整闭环..."

✅ "评审系统赶 7 月 1 号，Proma 被叫了 43 次。按时交了，人也废了。"

---

### 错误 3：回避问题

❌ "虽然遇到了一些技术挑战，但通过不断优化最终达成了目标..."

✅ "中间崩过两次，第三次才稳住。"

---

### 错误 4：编造细节

❌ "凌晨 3 点，我盯着屏幕，思考着架构设计的每一个细节..."

✅ 只写有证据支持的事实。没有凌晨 3 点的会话记录就不要写。

---

### 错误 5：Agent 评语写成第三人称

❌ "Proma 在本季度为用户提供了 279 次对话支持，主要集中在评审系统项目..."

✅ "你第一次叫我是 6 月 26 号，之后 279 次对话里有 136 次在搞评审系统。"

---

## 六、质量检查清单

生成 narrative 和 Agent 评语后，检查：

- [ ] **署名检验（最先做）**：拿掉署名，假装是真人朋友写的——你信吗？不信就重写
- [ ] 用了短句（平均 15 字以内）
- [ ] 开头直接进入事件，无铺垫
- [ ] 有具体数字、日期、项目名
- [ ] 有画面感或情绪感（至少 1 处）
- [ ] 有不确定性表达（"可能"、"也不知道"）
- [ ] 诚实表达了问题或失败
- [ ] 结尾留白，无总结无升华
- [ ] Agent 评语用第一人称
- [ ] 无"协助、支持、帮助"等正式词
- [ ] 无"成功、完美、卓越"等夸大词
- [ ] 所有数据有来源，无编造
